# SkinPlan v17.18.0 — Multi-user deployment checklist

## 1. Connect persistent user storage

In the Vercel project, install/connect **Upstash Redis** from Vercel Marketplace. The integration normally provides one of these supported environment-variable pairs:

- `UPSTASH_REDIS_REST_URL` + `UPSTASH_REDIS_REST_TOKEN`
- or `KV_REST_API_URL` + `KV_REST_API_TOKEN`

The Redis token must remain server-side. Never expose it in browser JavaScript.

## 2. Set the session secret

Add:

- `SKINPLAN_SESSION_SECRET` — at least 32 random characters; 64+ is preferable.

Example generator:

```bash
openssl rand -hex 32
```

## 3. Bootstrap the owner account once

For the first deployment, also set:

- `SKINPLAN_OWNER_USERNAME` — 3–40 lowercase-compatible characters; letters, numbers, dot, underscore and hyphen are supported.
- `SKINPLAN_OWNER_PASSWORD` — at least 10 characters. Prefer a long password generated by a password manager.

On the first login, if the SkinPlan user database is empty, the owner account is created and the password is stored only as a salted scrypt hash.

After the owner account exists, you may remove the two bootstrap owner variables and redeploy. Keep `SKINPLAN_SESSION_SECRET` and the Upstash credentials.

## 4. Owner workflow

1. Open the normal SkinPlan URL.
2. Sign in with the owner username/password.
3. The owner is taken to **SkinPlan Access Control**.
4. Create a customer username and temporary password.
5. Optionally add a customer/clinic note and a licence valid-through date.
6. Send the customer only the normal SkinPlan URL plus their username/password.

The customer is taken directly to the SkinPlan application and cannot access the owner panel.

## 5. Revoking or changing access

From Access Control:

- **Disable** — blocks the account immediately on the next server/session check.
- **Enable** — restores access.
- **Password** — sets a new password and revokes old sessions.
- **Rename** — changes the login username and revokes old sessions.
- **Expiry** — sets or clears an automatic licence expiry date and revokes old sessions.
- **Note** — stores an owner-only customer/clinic reference.

The owner account itself cannot be disabled, renamed or expired from the panel. Its password can be changed.

## 6. Password and session protections

- Passwords are salted and hashed with server-side `scrypt` using N=2^17, r=8, p=1.
- Session cookies are `HttpOnly`, `Secure`, and `SameSite=Strict`.
- Every protected API validates that the account is still active, unexpired, and on the current session version.
- Login attempts are limited per source+username using the same Redis store.
- Failed login messages do not disclose whether a username exists.
- Account-management POST requests require same-origin browser requests.

## 7. Keep the existing outer protection

Keep Vercel WAF/rate limits as an additional layer. Suggested starting points:

- `/api/login`: 5–10 failed attempts per several minutes per source.
- `/api/generate-report`: about 30 requests/minute per source.
- `/api/x3-report`: about 30 requests/minute per source.

The application also has an internal login limiter, but platform-level rate limiting reduces traffic before it reaches the function.

## 8. Repository and secrets

Keep the source repository private and require MFA for repository/Vercel access. Do not commit production secrets, Upstash credentials, owner bootstrap passwords, or customer passwords.

## 9. Product images and clinical engine

Product images continue to work as before. The 62 local packshots remain in `assets/products`, and fallback image retrieval remains behind the authenticated image endpoint. The decision engine, formulary rankings and scheduling rules remain server-side and are not shipped to customer browser JavaScript.
